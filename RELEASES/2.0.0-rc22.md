# 2.0.0-rc22

## Breaking changes

While Biff 2 is still in prerelease, I've included a warning that there may be
breaking changes before the official release. Biff 2 is now almost ready for
that release, and in preparation I do in fact have a few breaking changes to make
first before things get more locked in.

These changes only affect people who have started using the new Biff 2
libraries. If you've used Biff 1 but haven't tried out anything from Biff 2 yet,
none of these changes will be breaking if you do upgrade to Biff 2 later.

### biff.core: module-style components

Biff 2 now has "module-style" components instead of "function-style" components:
a module can have a pair of `:biff.core/start` and `:biff.core/stop` functions.
You still define the start order of components explicitly, but this is done by
defining a sequence of module ID keywords, each of which corresponds to a new
`:biff.core/id` key set on a module.

Before:

```clojure
(defn use-something [ctx]
  (let [something (start-something ctx)]
    (update ctx :biff.core/stop conj #(.close something))))

(def modules
  [...])

(def components
  [...
   use-something])

(require '[com.biffweb.core :as biff.core])

(defn start []
  (let [new-system (biff.core/start #'modules components)]
    ...))
```

Now:

```
(def something-module
  {:biff.core/id    :example/something
   :biff.core/start (fn [ctx]
                      (assoc ctx ::something (start-something ctx)))
   :biff.core/stop  (fn [ctx]
                      (.close (::something ctx)))})

(def modules
  [...
   something-module])

(def components
  [...
   :example/something])

(require '[com.biffweb.core :as biff.core])

(defn start []
  (let [new-system (biff.core/start #'modules components)]
    ...))
```

Each module you've registered that has a `:biff.core/start` function must have
its ID keyword present in the `components` sequence, otherwise you'll get an
error.

For backwards compatibility with Biff 1, function-style components (e.g.
`use-something`) are still supported, but they **must** use `:biff/stop` rather
than `:biff.core/stop`.

The system map returned by `com.biffweb.core/start` now contains a single
`:biff.core/stop-system` function instead of a vector of stop functions under
`:biff.core/stop`. As long as you're using `com.biffweb.core/stop` to stop your
system, no changes are needed.

#### Upgrading

All of the function-style components have been removed from the various Biff 2
libraries, and the corresponding modules have been created/updated to have start
and stop functions. If you've already started using the biff.core library,
you'll need to update your `components` vector to use module ID keywords, and
you'll need to ensure your `modules` vector includes the corresponding module.

  | Old                                    | New                                         | Module ID                            |
  | -------------------------------------- | ------------------------------------------- | ------------------------------------ |
  | `biff.config/use-aero-config`          | `(biff.config/module)`                      | `:biff.config/component`             |
  | `biff.sqlite/use-sqlite`               | `(biff.sqlite/module)`                      | `:biff.sqlite/component`             |
  | `biff.sqlite/use-litestream`           | `(biff.sqlite/litestream-module)`           | `:biff.sqlite/litestream`            |
  | `biff.sqlite/use-sqldef`               | `(biff.sqlite/sqldef-module)`               | `:biff.sqlite/sqldef`                |
  | `biff.sqlite/use-conn`                 | `(biff.sqlite/conn-module)`                 | `:biff.sqlite/conn`                  |
  | `biff.background/use-scheduled-tasks`  | `(biff.background/scheduled-tasks-module)`  | `:biff.background/scheduled-tasks`   |
  | `biff.background/use-queues`           | `(biff.background/queues-module)`           | `:biff.background/queues`            |
  | `biff.admin/use-alerts`                | `(biff.admin/module ...)`                   | `:biff.admin/alerts`                 |
  | `biff.ring/use-jetty`                  | `(biff.ring/module)`                        | `:biff.ring/jetty`                   |
  | `biff.xtdb/use-xtdb`                   | `(biff.xtdb/module)`                        | `:biff.xtdb/component`               |

There is also a new `(biff.background/module)` module, with ID
`:biff.background/component`, which includes both queues and scheduled tasks.

If you've defined any custom Biff 2 components, you can either change them to
use the new module format (recommended) or change them to use `:biff/stop`
instead of `:biff.core/stop` (less recommended).

#### Rationale

When a library provides both a component and a module, they often need to be
used together. The primary reason I kept modules and components separate until
now is that components' order matters while modules' order does not, and I
wanted users to define components' start order manually/explicitly rather than
computing the start order automatically somehow. The new approach prevents you
from registering a module but not the component or vice versa while still
requiring you to define the start order.

I also think bundling the start/stop lifecycle functions into modules is better
for code readability/conceptual understanding. e.g. modules already contained a
different "lifecycle" function, `:biff.core/init`.

### biff.fx: state functions have additional arguments

biff.fx state functions no longer always take a single `ctx` argument. The
`:start` function may have 0 or more additional arguments, and all arguments
passed to the machine function will be passed to the `:start` function. The
other state functions always take two arguments: the `ctx` map (same as before)
and an additional `input` map, which is the return value of the previous state
function. Output from previous state functions is no longer merged into `ctx`
(both for the `ctx` map passed to state functions and for the `ctx` map passed
to effect handlers).

To unit test a state function, set `:biff.fx/test <state keyword>` on `ctx`
instead of passing the state keyword in as the second argument.

As a convenience, keys for effect results returned from state functions starting
in `:_` are not passed on to subsequent state functions or included in the
final machine function return value. This lets you run effects (e.g. `:_stuff
[:example.fx/do-stuff ...]`) without having the effect result pollute the return
value, when the effect result isn't needed. Underscore-prefixed keys are still
included in unit test results (i.e. when setting `:biff.fx/test`).

Before:

```clojure
(fx/defmachine my-machine
  :start
  (fn [{::keys [a b]}]
    {:biff.fx/next :next
     :c            (+ a b)
     :stuff        [:example.fx/get-stuff]})

  :next
  (fn [{::keys [c stuff]}]
    ...))

(comment
  (my-machine {::a 2 ::b 3} :start)
  ; =>
  {:biff.fx/next :next
   :c            5
   :stuff        [:example.fx/get-stuff]})
```

Now:

```clojure
(fx/defmachine my-machine
  :start
  (fn [ctx a b]
    {:biff.fx/next :next
     :c            (+ a b)
     :stuff        [:example.fx/get-stuff]})

  :next
  (fn [ctx {:keys [c stuff]}]
    ...))

(comment
  (my-machine {:biff.fx/test :start} 2 3)
  ; =>
  {:biff.fx/next :next
   :c            5
   :stuff        [:example.fx/get-stuff]})
```

#### Upgrading

If you use biff.fx, you'll need to update your `fx/defmachine` / `fx/machine`
calls to have states other than `:start` take the second argument. You'll also
need to update unit tests to use `:biff.fx/test`. You do not need to update call
machine function call sites in your application code.

#### Rationale

When everything was merged into the `ctx` map, it wasn't always clear when
looking at a state function which parameters were in the original `ctx` map and
which were added by previous state functions. This change makes state functions
more readable: output from previous state functions is now passed in separately,
and `ctx` is always the same (except for the `:biff.fx/now` and `:biff.fx/seed`
keys which are given new values prior to each state function being called).

This change also makes fx machines more flexible since callers can pass them
multiple arguments instead of having to merge arguments into `ctx`.

### biff.ring: defroute is removed

The `biff.ring/defroute` macro has been removed. `defroute` was a wrapper over
biff.fx machines that:

- wrapped the machine in a Reitit route vector.
- used state keywords like `:get` and `:post` to define request methods.
- supported an "initial fx" vector that was used to run an effect before the
  first state function (e.g. a database or biff.graph query).
- autogenerated a Reitit path string if you don't provide one.
- rendered returned hiccup vectors as Ring response maps (`[:html ...]` ->
  `{:body "<html>...</html>", ...}`)

#### Upgrading

Define your Ring handlers as "regular" functions with `fx/defmachine`.
`defmachine` now supports an "initial fx vector" similar to what `defroute`
supported. Route paths and request methods should be defined inside your Reitit
routes vector instead of being defined next to the handler function. Since
`defroute` autogenerated a route path if you didn't provide one, you may need to
define a route path explicitly now. Return full response maps instead of hiccup
vectors.

biff.fx state functions also need to be defined in accordance with the changes
described above, although note that `defroute` already passed the initial fx
result as a second argument to your first state function.

Before:

```clojure
(defroute do-something
  [:biff.graph.fx/query [{:session/user [:user/email]}]]

  :post
  (fn [ctx {:keys [session/user]}]
    ...))

(def module
  {:biff.ring/routes
   [do-something]})
```

Now:

```clojure
(fx/defmachine do-something
  [:biff.graph.fx/query [{:session/user [:user/email]}]]

  :start
  (fn [ctx {:keys [session/user]}]
    ...))

(def module
  {:biff.ring/routes
   [["/my-page/do-something" {:post do-something}]]})
```

See also the next section about `path`.

#### Rationale

`defroute` was abnormal because it defines a route vector instead of just a
handler function, like doing `(def my-page ["/..." {:get ...}])` instead of
`(defn my-page [request] ...)`. This made unit testing a little inconvenient
since you typically just want to call the handler function without having to
extract it from a route. And since `fx/defmachine` is able to support the
"initial fx" vector syntax, the ergonomic benefits of `defroute` were small
enough that IMO they didn't outweigh defining routes in a non-conventional way.

The hiccup vector -> response map conversion also matters less when using
Datastar instead of htmx because with Datastar you typically have only a single
handler per page that returns HTML, and POST request handlers etc typically
return empty responses.

### biff.ring: path only takes template strings, not route vectors

The `path` function previously took either a Reitit path template string or an
entire Reitit route vector, in addition to some path/query parameters, and it
returned a concrete path string with parameters inserted. `path` was written to
work with the route vectors defined by `defroute`. Since `defroute` has been
removed, `path`'s support for route vectors has also been removed.

#### Upgrading

I recommend always using `defpath` instead of using `defpath` only for routes
referenced by multiple files and using `path` for routes referenced only in the
file in which they're defined.

Before:

```clojure
(defroute do-something "/do-something/:id"
  ...)

(defroute my-page
  ...
  [:form {:action (path do-something 123 {:a "b"})} ...])

(def module
  {:biff.ring/routes
   [do-something
    ...]})
```

Now:

```clojure
(defpath do-something-path "/do-something/:id")

(fx/defmachine do-something
  ...)

(fx/defmachine my-page
  ...
  [:form {:action (do-something-path 123 {:a "b"})} ...])

(def module
  {:biff.ring/routes
   [[(do-something-path) {:post do-something}]
    ...]})
```

If the function defined by `defpath` is called without any parameters, it
returns its path template string as-is. This is useful for defining your Reitit
routes without duplicating the path template string anywhere.

This approach also means you never have to use `declare` for routes that
reference each other.

### biff.graph: defresolver uses the new biff.fx format

Since `biff.graph/defresolver` wraps `biff.fx/machine`, it inherits the changes
to state functions. Previously, `defresolver` wrapped its state functions so
they all took the resolver input as a second argument. That is still the case
for the `:start` function, but other functions now receive the prior state
function's output as the second parameter.

#### Upgrading

If you want state functions other than `:start` to have access to the resolver
input, you should either pass the input along explicitly or get it from
`(:biff.graph/input ctx)`.

Before:

```clojure
(defresolver stuff-d
  {:input [:stuff/a
           :stuff/b]
   :output [:stuff/d]}

  :start
  (fn [_ctx {:stuff/keys [a b] :as _input}]
    {:biff.fx/next :next
     ::c           [:example.fx/get-c a b]})

  :next
  (fn [{::keys [c]} {:stuff/keys [a b] :as _input}]
    {:stuff/d (+ a b c)}))
```

After:

```clojure
(defresolver stuff-d
  {:input [:stuff/a
           :stuff/b]
   :output [:stuff/d]}

  :start
  (fn [_ctx {:stuff/keys [a b] :as _input}]
    {:biff.fx/next :next
     :stuff/a      a
     :stuff/b      b
     :stuff/c      [:example.fx/get-c a b]})

  :next
  (fn [_ctx {:stuff/keys [a b c] :as _input}]
    {:stuff/d (+ a b c)}))
```
